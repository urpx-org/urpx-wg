### 7\. Highly Dynamic Pricing
- Review findings from the highly dynamic pricing package and included ComEd RRTP / PG&E B-6 PDP examples
- Confirm modeling direction: separate HDP documents from static tariff structure and keep fixed charges outside automation streams
- Priority gaps: compact HDP ingestion, event representation, structured computation rules, API/feed modeling, and wholesale market references
- OpenADR 3.0 and Matter alignment for dynamic pricing communication
- Questions and feedback on scope and next steps for further development

Notes:
- This package contains ontology materials and so cannot yet be shared publicly, we are still undergoing IP review before being able to review publicly.
- BN notes that he has reviewed the gap analysis pages, and that he recognizes that mapping to Green Button may be a higher priority than highly dynamic pricing.
- KDS shares materials, we have a class for dynamic pricing and can create a document for highly dynamic pricing, but gaps still exist that we have reviewed with BN. 
- BN created a Google Doc with observations or items for discussion as feedback on the gap analysis for highly dynamic pricing representation.
- KDS explains some of the gap analysis focused on interoperability with other standards, asks whether WG members have input on standards mapping for highly dynamic pricing.
- BN says he has some notes on ideal standards for mapping in the Google Doc he shared.
- KDS says she will plan to review his notes and make changes and asks whether we can plan to have a separate check-in to follow up on highly dynamic pricing model development.
- KDS explains that the package contains diagrams showing where representation currently is, and also includes diagrams of proposed ontology additions for dynamic pricing modeling.
- BN confirms that the goal is to be able to get a price stream from any rate plan with HDP. Brings up case of tiered pricing, which is more complicated and requires future information, KDS agrees this is a complexity that requires representation of a customer scenario to allow for calculation of prices at exact time they can be calculated.
- KDS explains goal is to be able to represent total of all prices for each time period in which usage is measured.
- BN explains that MIDAS is in the process of updating to OpenADR 3 standard.
- KDS explains goal is that URPX can contain all rules and logic to calculate the price but also provide a standard output format for the results of this calculation
- BN explains that capacity requires a day-ahead data stream of forecast of usage. Not an easily accessible data stream.
KDS agrees it is not easily accessible, we hope to model everything in a structured way to allow for ease of calculation
- DJ says the idea that URPX could both describe the structure of tariff or components and maybe, for example with demand charges, if a tariff has a rule that charges increase due to tiers, or peak charge, he wonders where the link is between customer usage and the tariff.
- KDS agrees. The price can only be fully calculated for a given scenario, part of our current update is to include a scenario that includes customer profile and service point profile and usage data that is needed for computation. Once you've identified a rate plan for which you want to run a cost model, it will also prompt you for the inputs needed to perform the cost model.
- DJ confirms his understanding: URPX says here are some components of the price, but there are portions that a user may need to calculate if parameters are required user inputs.
- KDS agrees that we do not provide the output but do provide the structured data needed for calculation
- DC asks whether URPX will be just for electric utilities?
- KDS explains that this will work for all utilities
- BN explains that PGE has a price server to calculate wholesale market price, adder, etc... URPX could represent how prices are calculated.
- KDS says how those prices are calculated is out of scope but those prices are inputs to a rate plan model.
- KDS explains an URPX data custodian with API access may provide time series representation of rate plan prices, would need a given customer's scenario.
